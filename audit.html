1. Executive summary

Chromazen is in considerably better shape than the typical AI-assisted codebase. Pure logic — stroke smoothing, stamp spacing, coordinate transforms, manifest validation, persistence layout — is carefully written, validated at trust boundaries, and well tested. Premultiplied-alpha semantics are consistent across CPU compositing, GPU paths, eyedropper sampling, thumbnails, and export.

Significant risks concentrate in three areas:

  1. Background-worker lifecycle. Four controllers hand-roll the same detached-thread pattern. None survives a worker panic: the in-flight flag latches forever, blocking navigation and (in two cases) quit — force-quit then discards unsaved strokes.
  2. Autosave/export peak memory. Dirty-layer tracking limits PNG encoding, but every save still reads back, materializes, and thumbnail-resizes every layer. Peak transient memory is roughly 2× total layer bytes (~1.3 GiB for 10×4000²; ~13 GiB for 50 layers at 32 Mpx).
  3. GPU memory is bounded only in the middle. The 256 MiB history budget is real, but layer and reference counts are uncapped. Adding blank layers spuriously evicts stroke undo history.

Durability is good against process crashes (atomic project.toml via fsync-on-commit) but has a power-loss window: revision payloads are never fsynced, and the previous revision is deleted immediately after the pointer flips.

Nothing found corrupts data during normal operation. The interactive brush path is well-engineered for latency.

2. Architecture and data-flow

winit event
  └─ App::window_event
       ├─ PaintInputController → StrokeSmoother → StampQueue
       ├─ egui-winit (UI / references)
       └─ request_redraw
App::render  [RedrawRequested]
  ├─ drain completions (export / ref import / ref load)
  ├─ AppCommand queue
  ├─ AutosaveController::update
  ├─ GuiLayer (egui + native-texture previews)
  └─ PaintRenderer::render_to_view
       ├─ flush_stamps ≤1024 dabs → 1 buffer write → 1 instanced mask pass
       │     (smudge: 1 pass + 1 dab-rect copy per dab)
       ├─ dirty layer previews (128²)
       └─ blit: background + layers, scissored to visible canvas
Stroke: begin → mask (Max blend) → live preview → commit + history
History: per-stroke rect textures; structure ops retain PaintLayers; 256 MiB budget
Persistence: version counters → readback all layers → dirty PNG encode
  → temp dir → rename → atomic project.toml → delete previous revision

Boundaries are mostly coherent. PaintRenderer submodules have crisp responsibilities. App is the orchestration object: seven controllers and three interacting navigation flags.

3. Positive findings

  • Premultiplied-alpha consistency across CPU, GPU, eyedropper, thumbnails, and export — including hidden-base and chained clipping via shared clipping_base_index.
  • Input → GPU brush path designed for latency: desired_maximum_frame_latency: 1, instanced stamping, Max-blend mask accumulation, scissored commits.
  • Trust-boundary validation: pinned layer paths, brush stamp containment, reference decode limits, TOML reject of NaN / unknown fields.
  • Store failure handling: temp staging, commit re-read disambiguation, trash-rename deletion, corrupt artworks degrade to warnings.
  • Tests check behavior (spacing properties, premultiply round-trips, injected metadata failures), not implementation mirrors.
  • History mirror + swap achieves O(rect) undo/redo with no extra steady-state textures per operation.

F1

Worker panic permanently wedges navigation and quit

High · Confidence High · Concurrency

Each controller spawns a detached thread whose only completion signal is an mpsc message. The controller also holds a sender clone, so the channel never disconnects. If the worker panics, no completion arrives: ReferenceLoadController::is_loading() stays true (blocks exit and gallery); ExportController::exporting stays true (blocks quit from gallery); autosave in_flight stays set (status stuck on Saving).

Fix: wrap worker bodies in catch_unwind and always send a completion, or hold a JoinHandle and treat finished-with-no-message as failure. Prefer one shared helper (see F12).

F2

Autosave/export read back every layer at full resolution

High · Confidence High · Memory

Dirty tracking limits PNG encoding only. begin_document_layer_readback copies all layers; finish() materializes every layer as RgbaImage; thumbnail encoding Triangle-resizes every full-res layer even for metadata-only saves.

Cost: ~1.3 GiB transient for 10×4000²; ~13 GiB at 50×32 Mpx. Allocation failure here is the most likely F1 trigger.

Low-risk fix: read back only dirty layers; stream map → encode → drop per layer; build thumbnails from cached preview / last-saved PNG data.

Layer and reference counts are uncapped. Soft caps tied to a queried memory budget would bound the model.

F4

Revision payloads not fsynced; previous revision deleted immediately

Medium · Confidence High · Data safety

Layer PNGs, document.toml, and thumbnail use plain fs::write. project.toml is fsynced via atomic-write-file. Previous revision is removed immediately after. After power loss, the durable pointer can reference non-durable payload with N−1 already gone.

Fix: sync payload files and the revision directory before the pointer commit; delete N−1 lazily on the next successful commit.

F5

Smudge: one render pass + one copy per dab

Medium · Confidence Medium · Needs profiling

flush_smudge_stamps encodes a full-attachment Load/Store pass per dab, then a dab-rect copy. Dense small brushes produce hundreds of dabs per swipe. Severity depends on whether Metal skips untouched tiles.

Low-risk fix first: batch non-overlapping consecutive dabs into one pass. Confirm with GPU timestamps at fixed dab count across canvas sizes.

F6

Blank layer-adds charge full texture bytes into history budget

Medium · Confidence High · History

record_add charges layer_resource_byte_len() while detached is None. Four blank layers at 4000² (~244 MiB) evict essentially all stroke history; two adds do it at 32 Mpx.

Rect-based stroke retention is a known limitation documented in docs/undo-redo-plan.md — recorded as acknowledged, not a defect. The blank-add overcharge is an accounting bug within the current design.

F7

Synchronous decode on the main thread

Medium · Confidence High · Responsiveness

Artwork open decodes every layer PNG synchronously (seconds for 10×4000²). Gallery thumbnails decode inside the egui frame. References were made async; layers were not. Reuse the reference-load worker shape for layer decode.

F8

read_project(...).ok() treats corruption as first revision

Medium · Confidence Medium · Data safety

Corrupt / unreadable project.toml yields previous = None → revision 1. Most paths fail safely on ReuseCurrent; the damaging path needs all layers dirty and no references. Distinguish NotFound from other errors.

F9

Autosave depends on RedrawRequested delivery

Medium · Confidence Medium · Needs runtime confirmation

Autosave progress runs inside App::render. If macOS suppresses draws while miniaturized, paint → minimize within the 2 s debounce may never save. Drive autosave.update from new_events / about_to_wait if confirmed.

F10

Eyedropper blocks main thread on GPU-queue drain

Low–Med · Confidence High · Responsiveness

device.poll(PollType::wait_indefinitely()) waits for all outstanding GPU work. Sampling is stroke-gated and throttled to 33 ms — acceptable, but magnifies under GPU load. Persistent readback buffer + one-frame-stale results would remove the wait.

F11–F12

Navigation flags and duplicated workers

Low–Med · Architecture

Three mutable flags encode gallery / new-artwork / exit transitions implicitly. Replace with one PendingNavigation enum. Four controllers reimplement sender+receiver+wake+spawn with three different in-flight representations — why F1 exists four times. A small Job<T> helper consolidates them.

7. Open questions

  • Does macOS deliver RedrawRequested for miniaturized windows in winit 0.30? (F9)
  • Does Apple’s TBDR skip load/store for tiles untouched by geometry? (F5)
  • Two app instances share the store with no locking — double-launch risk
  • Worker-thread device.poll during main-thread render — Metal scheduling hiccups?

10. Benchmark plan

On 4000² and 8192×4096, with 1 / 10 / 50 layers:

  1. Brush/smudge latency — sparse vs dense, 20 px vs 300 px; GPU ms vs canvas area at fixed dab count
  2. Autosave peak RSS + wall time — metadata-only, single-dirty, all-dirty
  3. Eyedropper frame-time while option-dragging
  4. Click-to-editor and first-gallery-frame timing
  5. References: 10 × 16 Mpx import / pan / zoom memory
  6. Undo near budget with blank layer-adds interleaved

11. Five highest-value changes

  1. Panic-safe shared worker helper (F1/F12). Benefit: eliminates unquittable-app scenario. Risk: low. Proof: injected-panic tests; app remains navigable.
  2. Dirty-only streamed autosave readback (F2). Benefit: ~10× peak-memory reduction; removes most likely F1 trigger. Risk: moderate. Proof: peak-RSS before/after at 10/50 layers.
  3. fsync revision payloads + deferred N−1 deletion (F4). Benefit: closes the real data-loss window. Risk: low. Proof: failure-injection + hard-poweroff VM test.
  4. History accounting: zero-charge blank adds, granularity clamp (F6/F16). Benefit: undo survives ordinary layer management. Risk: low. Proof: unit test + Metal capture near budget.
  5. Async artwork-open layer decode (F7). Benefit: removes worst interactive freeze. Risk: low (proven template). Proof: click-to-editor timing.

The interactive painting core — smoothing, stamping, masking, preview, commit — needs no architectural change. Highest-leverage work is in the lifecycle seams: workers, saves, and memory bounds.
